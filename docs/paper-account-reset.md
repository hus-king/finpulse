# Owner-scoped paper account reset

The operator-only `backend.quant.maintenance.reset_peg_account` implements an explicitly requested paper account reset. There is no public HTTP reset route. Call it only for the account identified by the human, with a fresh expected configuration revision and one UUID retained for retries.

The existing owner-row transaction lock protects the operation. An active quant execution lease or revision conflict stops the reset. Before replacing the active book, the transaction saves the original account, fills, configuration, decisions, daily turnover and runtime/opening state in `paper_reset_archive/<reset UUID>` for that owner. The archive contains original row keys/timestamps and a SHA-256 of the records. Retrying the same UUID returns its original result; it does not reset a subsequent balance again.

The new book has the original200,000 CNY cash, empty positions, zero PnL/fees and sequence0. Old active fills and decisions are removed only after being archived in the same transaction. Retired request UUIDs remain in a separate owner-scoped index so a delayed old order cannot spend the reset balance. Authentication, watchlists, user strategy definitions and shared market/PEG/news caches are retained. Configuration keeps PEG top5/all, increments its revision and resets the equity peak and daily turnover state.

A private `quant_opening/once` marker binds the reset UUID, owner, new configuration revision, PEG strategy ID and next verified trading date. Only this reset account may start its first daily PEG plan after09:30 on that date. Session/calendar validation, live quote freshness, daily decision uniqueness, T+1, price/corporate-action checks, fees,5-position/20%-per-name/80%-total/30%-daily-turnover and drawdown limits remain in force. Default strategies/accounts keep their10:00 start. Quote-unavailable/stale errors for the opening plan retry after60 seconds; other failures retain300 seconds. Obsolete workers cannot write a retry state over a new configuration revision.

Operational verification must establish an archived original ledger, empty live positions/fills/decisions,200,000 CNY cash/equity, PEG5/all enabled, matching opening marker and running server scheduler. An opening marker is scheduling readiness, not proof of a future fill. Validate the opening execution with actual trading-session data; do not change the production clock or fabricate quotes. Initial allocation still respects the30% turnover limit and can differ from the80% target.

Validation for this change:10 new reset/opening regressions and426 total Python tests passed locally. The tests cover transactional rollback, UUID replay, active-lease/revision conflict, owner isolation, delayed old orders, stale-worker runtime writes, closed-session/quote gates, default10:00 behavior and a single five-stock first plan under the existing turnover limit. Copilot requested_model=auto reviewed the supplied anonymous code; no account data was delegated. Its final review found no concrete bugs.
