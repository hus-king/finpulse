# 热点新闻的事件筛选标准

## 选什么

先识别新闻事件，再考虑市场传导。入选应同时满足：

1. 有明确主体，能回答“谁具体做了什么、发生了什么变化”。
2. 有新增事实：新政策、重大事故/安全反馈、监管调查、重要新品、停航停产、重要经营变动等。计划内发布也算新变化，不只接收字面上的突发事故。
3. 有足够的重要性：国内国际公共事件、重要产业变化、知名品牌的重要产品或安全事件。不能以“如果推广可能带动某行业”将小事放大。
4. 有报道材料支持。投诉、测评和官方回应分别归属，不能把报告了争议当成缺陷已获确认。平台上榜和资讯发布时间也不等于事实已独立核验。

筛选依据不足不对用户展示；后台保留审计，不提供“待核实/排除/全部话题”的公共列表。不凑满条数，不以新闻之后股票是否涨跌来筛选。

## 不应入选的例子

| 话题 | 不入选的原因 |
| --- | --- |
| “看不见的外贸”畅跑全球 | 背景/趋势及成就叙述，不能只因出现AI、电力、贸易就入选 |
| 超长预售45天原来是在等退货回来 | 日常消费现象和经营机制解释，没有重要主体的新事件 |
| 冷冻烘焙卖3块，精品面包卖30块 | 商业模式/成本比较，不是重要新变化 |
| 人造古镇为啥集体哑火 | 长期问题的归纳；若某大型运营商正式破产则另作具体新事件判断 |
| 有KTV的列车火了 | 小范围体验和消费讨论，不靠假设推广提升为大事 |
| 深圳禁鸣喇叭，咋知道谁按的 | 对已有技术/规则的解释；若明确发布重要新规则重新判断 |
| 指数涨幅扩大至1%、常规日度报价 | 行情描述本身不是事件；熔断或有新催化的异常变动另议 |
| 手机值不值得买、个人使用感受 | 个人观点不是新品发布、可归属的安全反馈或监管行动 |

“重大”仍需要编辑判断。代码约束主体/引文存在、重要性及新增性枚举，加上保守规则和反例；它们不能自动证明语义判断正确。先用明确反例防回归，再扩大独立人工标注样本评价漏选与误选，不用自编规则测试通过冒充真实准确率。

## 数据与热度分工

- 百度/微博：提供平台上榜线索、原始名次与采集时间；不是事实核验源。
- Tushare兼容新闻接口：`news`提供快讯、`major_news`提供通讯与正文，主要用作新闻材料。`major_news`这个接口名不保证内容重大；普通行情、例行财报和小事仍需排除。
- 资讯接口没有热搜名次，也通常不提供原报道URL。页面明确显示报道时间、实际来源和“来源入口”，不编造热度，不把来源首页当作文章原文。
- 当前先接财联社、新浪、华尔街见闻和新闻通讯，查询最近24小时；每源至多100行，优先选择具体事件候选及较新报道、保留15条进入后续筛选，避免无界付费推理。新闻与平台热榜同标题合并，尚未做到所有语义相似报道自动合并。
- 接口正文只用于后端分析，公共榜单不返回内部完整正文；个股分析结合报道材料与本公司的主营证据。

## 更新请求与配置

`POST /api/hot-news/refresh`启动共享后台任务，运行中返回202，页面每2秒通过只读GET获取进度。采集和模型处理不再占着同一个长HTTP请求；离开页面任务继续。重复请求加入已有任务，任务失败和服务重启有明确状态，可重试。旧筛选版本会重新筛选。

密钥只放服务端`config.local.json`中的`tushare_news`对象，或与真实配置文件同目录的`news-provider.local.json`，内容包含`base_url`和`token`；配置文件权限600且被Git忽略。支持用户提供的兼容服务地址，不将其当成官方Tushare服务；不把token放在前端、来源链接、错误正文或Git。无需安装Python SDK或网站MCP服务器，直接使用兼容REST协议。

2026-10-26小量实测：财联社、新浪、华尔街见闻快讯、新闻通讯、新闻联播均返回code=0。此结果只证明当前这些接口可读，不等于订阅永久有效或所有返回内容可靠。权限过期会明确降级，不伪造数据。
